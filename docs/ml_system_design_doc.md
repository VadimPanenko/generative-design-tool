*Дизайн-документ разработан на основе шаблона от [Reliable ML](https://github.com/IrinaGoloshchapova/ml_system_design_doc_ru)*

## 1. Цели и предпосылки

### 1.1. Зачем идем в разработку продукта?

**Бизнес-цель:**

Создать AI-сервис для автоматической генерации иконок и графических материалов в корпоративном стиле, который:
- Сокращает время создания визуального контента с 2-3 часов до 20-40 минут
- Автоматически применяет корпоративный стиль и цвета из бренд-бука
- Снижает зависимость от внешних подрядчиков и специалистов 3D-моделирования

**Почему станет лучше от использования ML:**

| Аспект | Как сейчас | Как будет с AI-сервисом |
|--------|-----------|------------------------|
| Время создания | 2-3 часа ручной работы в 3D-редакторах | 1-4 минуты автоматической генерации |
| Навыки | Требуются навыки 3D-моделирования | Простое текстовое описание на русском |
| Стиль | Ручное согласование с бренд-буком | Автоматическое применение корп. стиля |
| Итерации | Множественные согласования | Быстрые правки через inpainting |
| Подрядчики | Высокие затраты на специалистов | Внутренний инструмент для типовых задач |

**Критерии успеха итерации:**

- Сокращение времени создания графики минимум на **70%**
- Положительная обратная связь от **60%+** дизайнеров
- Использование сервиса для **30%+** новых задач по созданию 3D-иконок
- Соответствие бренд-буку в **70%+** случаев без ручной доработки
- Снижение итераций согласования на **30%**

---

### 1.2. Бизнес-требования и ограничения

**Функциональные требования:**
- 3D изображения в PNG формате без фона, в корпоративной стилистике
- Генерация предметов, 3D значков, ассетов для интерфейсов и презентаций
- Время генерации 1024x1024px не более 4 минут
- Простой веб-интерфейс с промптами на русском языке
- Автоматическое применение корпоративных цветов

**Бизнес-ограничения:**
- Использование внутренних GPU-серверов с ограниченными ресурсами
- Все данные хранятся внутри корпоративной инфраструктуры
- Ограниченный бюджет на внешние вычислительные ресурсы

**Описание бизнес-процесса пилота:**

1. **Фаза тестирования** (1-2 месяца): 5-7 дизайнеров тестируют параллельно с традиционными методами
2. **Фаза расширения** (2-3 месяца): Доступ для всей дизайн-команды (15-20 человек)
3. **Оценка результатов**: Сравнение времени, анализ удовлетворенности, подсчет экономического эффекта

**Критерии успешного пилота:**
- Adoption rate ≥ 60% (регулярное использование)
- Качество: ≥ 70% соответствие бренд-буку
- NPS ≥ 40
- Экономия ~10 часов/неделю для пилотной группы

---

### 1.3. Что входит в скоуп проекта/итерации

**Входит в скоуп MVP:**

*Функциональность:*
- Генерация 3D-иконок по текстовому описанию
- Автоматическое обогащение промптов с учетом корпоративных гайдлайнов
- Применение корпоративных цветов
- Веб-интерфейс с базовым функционалом
- Dual prompting (T5 + CLIP)

*Технические аспекты:*
- Развертывание на GPU-серверах (A40)
- Интеграция FLUX.1-dev для генерации
- Интеграция DeepSeek-R1 / Qwen2.5 для обогащения промптов
- Документация разработки

**НЕ входит в скоуп MVP:**
- Inpainting, upscaling, удаление фона
- Хранение истории промптов
- Плагин для Figma
- Генерация русскоязычного текста на изображениях
- Файн-тюнинг моделей на корпоративных данных
- RAG-система для промптов
- API для интеграции с другими системами
- Batch-генерация

---

### 1.4. Предпосылки решения

**Выбор блоков данных:**

1. **Корпоративные гайдлайны**: Цветовая палитра, стилистические требования, примеры 3D-иконок
   - *Обоснование*: Необходимы для автоматического применения корпоративного стиля

2. **История промптов и изображений**: Промпты пользователей, сгенерированные изображения, оценки качества
   - *Обоснование*: Анализ эффективности, накопление базы успешных промптов

3. **Обратная связь**: Оценки соответствия бренд-буку, комментарии, метрики использования
   - *Обоснование*: Критична для итеративного улучшения системы

**Технологический стек:**

| Компонент | Решение | Обоснование |
|-----------|---------|-------------|
| Генеративная модель | FLUX.1-dev | State-of-the-art качество, хорошее понимание промптов, возможность кастомизации |
| LLM для промптов | DeepSeek-R1 / Qwen2.5 | Поддержка русского языка, быстрая обработка |
| Инфраструктура | GPU NVIDIA A40 (48GB) | Требования безопасности, достаточные ресурсы |
| Backend/Frontend | FastAPI + веб-интерфейс | Быстрая разработка, легкая интеграция с ML |

**Гранулярность и горизонт:**
- Real-time генерация по запросу
- Одно изображение за один промпт
- Персонализация на уровне пользователя

**Предположения о поведении пользователей:**
- Формулировка запросов на русском в свободной форме
- 3-5 генераций за сессию с итеративными улучшениями
- Основной use-case: отдельные иконки, не сложные сцены

## 2. Методология

### 2.1. Постановка задачи

**Техническая формулировка:**

Разработка **генеративной системы text-to-image** с автоматическим стиль-адаптером для создания графических материалов в корпоративном стиле.

**Компоненты задачи:**

1. **Text-to-Image генерация**: Преобразование текста на русском в изображения
2. **Автоматическое обогащение промптов**: NLP-обработка через LLM, добавление стилистических параметров, перевод на английский, генерация negative prompts
3. **Оркестрация пайплайна**: Управление последовательностью вызовов моделей, обработка результатов

**Типы задач:**
- Основная: Условная генерация изображений (Conditional Image Generation)
- Вспомогательная: Улучшение текста (Text Enhancement)

**Метрики оценки:**
- **Технические**: Время генерации, использование GPU, throughput
- **Качественные**: CLIP score, соответствие бренд-буку (экспертная оценка)
- **Бизнес**: Процент использования, удовлетворенность, экономия времени

## Этап 1. Подготовка данных

### Цель этапа
Обеспечить наличие всех необходимых данных для работы системы и провести их качественный анализ.

### Описание данных и сущностей

> **Примечание:** Ниже подробно описаны все типы данных, используемые в системе, с указанием структуры экземпляров и способов использования.

---

#### 1. Тестовые промпты пользователей

**Описание:** Текстовые запросы на русском языке, описывающие желаемое изображение.

**Источник:** Собраны во время интервью с дизайнерами (5 встреч), а также синтезированы на основе анализа типовых задач дизайн-отдела.

**Цель сбора и анализа:** 
- Понять, как дизайнеры формулируют запросы в естественной форме
- Выявить паттерны (короткие/длинные, наличие технических терминов)
- Определить необходимость системы обогащения промптов
- Сформировать тестовый набор для оценки качества генерации

**Структура экземпляра данных:**

| Поле | Тип | Описание | Пример |
|------|-----|----------|--------|
| `prompt_id` | string | Уникальный идентификатор | "p_001" |
| `text` | string | Текст промпта на русском | "красивая иконка автомобиля" |
| `category` | string | Категория объекта | "техника", "UI", "бизнес" |
| `complexity` | enum | Сложность запроса | "простой", "средний", "сложный" |
| `source` | string | Источник промпта | "интервью", "синтетический" |
| `has_style_hint` | boolean | Есть ли указание на стиль | false |
| `word_count` | int | Количество слов | 4 |
| `char_count` | int | Количество символов | 28 |

**Пример записи:**
```json
{
  "prompt_id": "p_015",
  "text": "3D иконка смартфона в изометрии для мобильного приложения",
  "category": "UI",
  "complexity": "средний",
  "source": "интервью",
  "has_style_hint": true,
  "word_count": 8,
  "char_count": 54
}
```

**Результаты анализа промптов:**
- Средняя длина: ~35 символов (короткие, неинформативные)
- Только 6% содержат явное указание стиля
- Преобладающие категории: UI-элементы (22%), техника (18%), бизнес (16%)
- **Вывод:** Необходима система обогащения промптов через LLM

#### 2. Корпоративный бренд-бук

**Описание:** Документ с правилами оформления визуальных материалов в корпоративном стиле.

**Источник:** Внутренняя документация компании (Figma, PDF).

**Цель использования:** Извлечение правил для автоматического добавления стилистических параметров в промпты.

**Структура данных из бренд-бука:**

| Компонент | Формат | Количество | Использование |
|-----------|--------|------------|---------------|
| Цветовая палитра | HEX-коды | 8 основных цветов | Инъекция в промпты |
| Типографика | Названия шрифтов | 3 семейства | Справочно |
| Примеры 3D-графики | Изображения (описания) | ~15 примеров | Анализ стиля |
| Правила композиции | Текстовые описания | ~10 правил | Системный промпт LLM |
| Запрещённые практики | Текстовые описания | ~8 пунктов | Negative prompts |

**Формализованная цветовая палитра:**

| Название | HEX-код | Использование |
|----------|---------|---------------|
| Primary Blue | #005BFF | Основной акцент |
| Light Blue | #00A0FF | Вторичные элементы |
| Accent Pink | #FF1493 | Акценты |
| White | #FFFFFF | Фон, контраст |
| Dark | #1A1A1A | Тени |
| ... | ... | ... |

#### 3. Примеры 3D-иконок (референсы)

**Описание:** Существующие 3D-иконки, созданные дизайнерами вручную, соответствующие корпоративному стилю.

**Источник:** Библиотека дизайн-компонентов в Figma.

**Цель использования:**
- Экспертная оценка качества генерации (сравнение с референсами)
- Анализ стилистических особенностей (освещение, материалы, углы)
- Валидация соответствия бренд-буку

**Структура экземпляра данных:**

| Поле | Тип | Описание | Пример |
|------|-----|----------|--------|
| `image_id` | string | Уникальный идентификатор | "ref_042" |
| `file_path` | string | Путь к файлу | "icons/3d/smartphone.png" |
| `category` | string | Категория объекта | "техника" |
| `object_name` | string | Название объекта | "смартфон" |
| `resolution` | string | Разрешение | "1024x1024" |
| `has_transparency` | boolean | Прозрачный фон | true |
| `style_tags` | list[string] | Стилевые теги | ["isometric", "soft_shadows"] |
| `creation_date` | date | Дата создания | "2024-03-15" |
| `author` | string | Автор | "designer_a" |

**Статистика по референсам:**
- Общее количество: ~200 изображений
- Форматы: PNG (95%), SVG (5%)
- Разрешения: 1024x1024 (80%), 512x512 (15%), другие (5%)
- Все с прозрачным фоном

**Важно:** Этот объём (200 изображений) недостаточен для fine-tuning модели (требуется 1000+), поэтому используется как validation set для экспертной оценки.

#### 4. Предобученная модель FLUX.1-dev

**Описание:** Диффузионная модель для генерации изображений по текстовым описаниям.

**Источник:** HuggingFace (black-forest-labs/FLUX.1-dev)

**Структура файлов модели:**

| Файл | Размер | Назначение |
|------|--------|------------|
| flux1-dev.safetensors | 23.8 GB | Основные веса модели |
| ae.safetensors | 335 MB | Variational Autoencoder |
| t5xxl_fp16.safetensors | ~10 GB | T5 Text Encoder |
| clip_l.safetensors | ~250 MB | CLIP Text Encoder |
| config.json | 2 KB | Конфигурация |

**Параметры модели:**
- Архитектура: Rectified Flow Transformer
- Размер: ~12B параметров
- Поддерживаемые разрешения: до 4096x4096
- Dual text encoding: T5 + CLIP

---

#### 5. LLM модели для обогащения промптов

**Описание:** Языковые модели для преобразования пользовательских промптов.

**Модели:**

| Модель | Назначение | Размер | Квантизация |
|--------|-----------|--------|-------------|
| DeepSeek-R1-671B-AWQ | Сложные задачи обогащения | 671B → ~200GB | AWQ 4-bit |
| Qwen2.5-14B-Instruct | Быстрые операции (перевод, negative) | 14B → ~10GB | FP16 |

**Системные промпты (примеры):**

```
# Для обогащения промптов
You are an expert prompt engineer for FLUX.1 image generation.
Transform the user's brief description into a detailed prompt:
1. Add "3D render", "isometric view", "soft lighting"
2. Include corporate colors: #005BFF, #00A0FF
3. Keep the core object from original prompt
4. Output in English only
```

## Этап 2. Подготовка прогнозных моделей

### Цель этапа
Настроить и валидировать модели для генерации изображений и обогащения промптов.

### Особенность проекта: Inference-only подход

> **Важно:** В данном проекте используется подход **inference-only** — предобученные модели применяются без дополнительного обучения (fine-tuning). Это обосновано спецификой задачи.

#### Почему не обучаем модели с нуля или не делаем fine-tuning

**1. Недостаток данных для fine-tuning:**
- Имеется ~200 референсных изображений
- Для качественного fine-tuning диффузионных моделей требуется 1000-5000+ изображений одного стиля
- Риск overfitting на малом датасете

**2. Качество предобученных моделей:**
- FLUX.1-dev обучена на миллиардах изображений
- Модель уже "знает" концепции 3D-рендера, изометрии, корпоративного стиля
- Нужно только правильно "попросить" через промпт

**3. Специфика generative AI:**
- В отличие от классификации/регрессии, генеративные модели оцениваются по качеству выхода
- "Функция потерь" существует только на этапе pre-training (diffusion loss)
- На inference мы не оптимизируем loss, а оцениваем качество генерации

**4. Экономическая эффективность:**
- Fine-tuning FLUX требует 100+ GPU-часов на A100
- Промпт-инженеринг даёт 75% usability без дополнительных затрат
- MVP можно запустить немедленно

### ML-метрики и их обоснование

> **Примечание:** Поскольку модели не обучаются (inference-only), классические loss-функции не применимы. Используются метрики оценки качества генерации.

#### Метрики качества генерации

| Метрика | Формула/Описание | Целевое значение | Обоснование выбора |
|---------|------------------|------------------|-------------------|
| **CLIP Score** | `cosine_similarity(CLIP(image), CLIP(prompt))` | ≥ 0.25 | **Почему:** Стандартная метрика для text-to-image. Измеряет семантическое соответствие изображения тексту. Исследования показывают корреляцию с человеческой оценкой (r=0.7). **Связь с бизнесом:** Высокий CLIP Score означает, что изображение соответствует запросу дизайнера → меньше итераций доработки. |
| **FID** | `FrechetDistance(Inception(real), Inception(generated))` | ≤ 50 | **Почему:** Измеряет реалистичность и качество изображений сравнением распределений признаков. Низкий FID указывает на высокое качество рендера. **Связь с бизнесом:** Реалистичные 3D-иконки требуют меньше ручной доработки → экономия времени. |
| **Экспертная оценка** | Шкала 1-5 от арт-директора | ≥ 3.5 | **Почему:** Автоматические метрики не улавливают соответствие бренд-буку. Только эксперт может оценить стилистическую согласованность. **Связь с бизнесом:** Прямая связь с бизнес-целью "70%+ соответствие бренд-буку". |
| **Usability Rate** | `count(usable) / count(total)` | ≥ 70% | **Почему:** Ключевой практический показатель — может ли дизайнер сразу использовать результат. **Связь с бизнесом:** Напрямую влияет на экономию времени (цель: 70% сокращение). |

#### Почему не используются классические loss-функции

| Классический подход | Почему не применим в нашем случае |
|---------------------|-----------------------------------|
| MSE/MAE Loss | Требует пары (вход, целевой выход). У нас нет "правильных" изображений для каждого промпта. |
| Cross-Entropy | Применима для классификации. Генерация — не классификация. |
| Diffusion Loss | Используется только при pre-training. На inference модель уже обучена. |
| Perceptual Loss | Требует fine-tuning. Мы используем inference-only подход. |

**Ключевое отличие generative AI:**
В классическом ML мы минимизируем ошибку предсказания. В generative AI мы оцениваем качество сгенерированного контента постфактум через метрики и экспертные оценки.

### 3.2. Критерии успешного пилота

| Категория | Метрика | Целевое значение | Вес |
|-----------|---------|------------------|-----|

| **Quality** | Satisfaction Score | > 3.5/5 | 15% |
| **Efficiency** | Сокращение времени создания | ≥ 70% | 20% |
| **Satisfaction** | NPS | ≥ 40 | 10% |
| **Stability** | Success rate генерации | > 95% | 10% |

#### Формула успешности пилота

```
Pilot_Success = (Adoption ≥ 60%) AND (Quality ≥ 70%) AND (NPS ≥ 40) AND (TimeSaving ≥ 70%)
```

**Все четыре условия должны выполняться для признания пилота успешным.**

#### Критерии неудачи (требуется пересмотр)

| Метрика | Критическое значение | Действие |
|---------|---------------------|----------|
| Adoption | < 40% | Пересмотр UX, дополнительное обучение |
| Качество | < 40% | Пересмотр промпт-инженеринга |
| NPS | < 0 | Глубокое исследование причин |
| Time Saving | < 40% | Анализ bottlenecks в процессе |

#### Промежуточные контрольные точки

| Неделя | Проверяемые метрики | Минимальный порог |
